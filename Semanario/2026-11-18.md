# Aula 10 — Deploy no Render (18/11/2026)

## O que eu aprendi
Como colocar o projeto no ar de verdade usando o Render, com o front-end (React + Vite) e o back-end (Express) saindo do mesmo servidor e o banco no Turso, que configuramos na aula passada.
Também entendi que o servidor da nuvem começa "do zero": ele só tem o que está no repositório, então tudo o que o projeto precisa para rodar tem que estar descrito nos scripts e no `render.yaml`.

## Principal dificuldade
O `server.ts` do meu repositório não era igual ao da apostila: ele não tinha a rota `/api/version`, que era a referência para saber onde colar a rota `/api/db-check`.
Na pasta base do dia também encontrei um problema no `.gitignore`: todas as linhas começavam com um espaço, e assim o Git não reconhece nenhum padrão. Se eu tivesse feito o `git add .` com ele, o `.env` com o token do Turso e a `node_modules` iriam para o GitHub.

## Como eu resolvi
Coloquei a `/api/db-check` logo depois da `/api/health` e antes da `/api/auth/register`, que é a mesma região que a apostila indica.
Tirei os espaços do começo das linhas do `.gitignore` e conferi com `git status` que o `.env`, a `web/dist` e o `tarefas.db` não entravam no commit.
Antes do push rodei `npm run build` e subi o servidor localmente para testar `/api/health`, `/api/db-check` e o F5 em `/tarefas`.

## Observações (opcional)
A rota `/api/db-check` ajuda muito: em vez de só dizer que o servidor está de pé, ela mostra quais tabelas existem e quantos registros cada uma tem, o que confirma que a produção está realmente usando o banco certo.

## Diário de Bordo

**1. Por que o script de build precisou do `npm --prefix web install` antes do `npm run build:web`?**
O `npm install` do Render instala só as dependências da raiz. O front-end tem o próprio `package.json` dentro de `web/`, e sem instalar essas dependências o Vite e o TypeScript do front não existem no container, então o build falha.

**2. Qual é a função do `render.yaml` e por que `buildCommand` e `startCommand` exigem atenção?**
É a configuração do serviço escrita em arquivo (nome, runtime, plano, comandos, variáveis e health check), que fica versionada junto com o código. O `buildCommand` precisa ter `npm run build`, porque o padrão do Render é só `npm install`, e sem isso a `web/dist` nunca é gerada e o front não aparece. O `startCommand` é o que mantém o servidor rodando; se estiver errado, o deploy termina mas o site não sobe.

**3. Por que o `JWT_SECRET` pôde ficar em branco e o `TURSO_URL`/`TURSO_TOKEN` não?**
O `JWT_SECRET` é só uma chave aleatória que assina os tokens, então o `generateValue: true` deixa o próprio Render gerar uma. Já o `TURSO_URL` e o `TURSO_TOKEN` apontam para um banco que já existe na minha conta do Turso; o Render não tem como adivinhar esses valores (`sync: false`), por isso precisam ser copiados manualmente.

**4. Qual é a finalidade da rota `/api/db-check`?**
Confirmar em produção que o servidor está conectado ao banco certo: ela faz um `SELECT 1`, lista as tabelas (`usuarios` e `tarefas`) e mostra quantas linhas cada uma tem. Se o banco não responder, devolve `503` com a mensagem de erro.

**5. Por que rodar `npm run build` localmente antes do `git push`?**
Porque com o `autoDeploy` cada push na branch dispara um deploy. Se o build quebra no meu computador, também vai quebrar no Render; testando antes eu acho o erro em segundos, sem esperar minutos de deploy e sem derrubar a versão que está no ar.

**6. O que aconteceu ao dar F5 em `/tarefas`?**
A página carregou normalmente, sem 404. Isso acontece porque o Express tem uma rota curinga no final que devolve o `index.html` para qualquer caminho que não seja `/api`, e aí o React decide qual tela mostrar.

**7. Encontrou algum erro? Qual foi a causa e a solução?**
Não deu erro no build, mas encontrei o problema do `.gitignore` com espaços no começo das linhas, que teria publicado o `.env` com o token do banco. Corrigi antes do commit. A outra diferença foi a falta da rota `/api/version`, resolvida colocando a `/api/db-check` logo depois da `/api/health`.
